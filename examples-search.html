SF01 · Search & Navigate

Type to query the tree. Filter mode hides non-matching nodes and auto-expands ancestors of matches. Search mode keeps the whole tree visible and jumps between matches. Use Enter for next, Shift+Enter for previous, Esc to clear. Toggle the mode with the icon button. Tick checkboxes while filtered — the checked list keeps what you picked.

Note

The search index is built asynchronously after the data is set. If no results appear on the very first keystroke, wait a moment for indexing to finish (the status line above says when it is ready).

// Enable the internal index + point it at the label member
tree.isInternalSearchIndexEnabled = true;
tree.searchValueMember = 'name';

function onInput() {
  const text = input.value.trim();
  if (mode === 'filter') tree.filterNodes(text);   // prune the tree
  results = tree.searchNodes(text);                 // query without pruning
  if (results.length) navigateTo(0);
}

function navigateTo(i) {
  tree.scrollToPath(results[i].path, { shouldExpandAncestors: true, shouldHighlight: true });
}

SF02 · Filter vs Search

Both methods consult the same index, but they do different things to the tree. Run the two live demos below with the same query to feel the difference.

SF03 · Internal Search Index (FlexSearch)

Search is backed by an internal FlexSearch index, built asynchronously off the node data. It is on by default (isInternalSearchIndexEnabled); tell it which value to index via searchValueMember (or the getSearchValueCallback for multi-field / computed text). Without the index enabled, filterNodes / searchNodes have nothing to query.

Property Attribute Type Description
isInternalSearchIndexEnabled enable-internal-search-index boolean Build the internal FlexSearch index (required for search/filter). Default true; false = no index, search finds nothing
searchValueMember search-value-member string Property name whose value gets indexed (e.g. "name")
getSearchValueCallback — (set as JS property) ({ node }) => string Custom extractor — index multiple fields / computed text
indexerBatchSize indexer-batch-size number Max nodes indexed per idle slot (default 1000; each slot is also time-boxed)
indexerTimeout indexer-timeout number Idle timeout (ms) between index batches (default 50)
initializeIndexCallback — (set as JS property) () => Index Factory for a custom FlexSearch Index (tokenizer, charset, …) instead of the built-in one; a change rebuilds the index
searchTerm search-term string | null The active filter term — the declarative twin of filterNodes(text)
maxSearchResultCount max-search-result-count number Max matches a search / filter returns (default 1000); search-status-change reports isLimited
filterScope filter-scope 'matches' | 'descendants' | 'tree-depth' | 'subtree-height' | 'levels-below' Experimental. Which descendants of a filter match stay visible (ancestors always do): matches (default), descendants (whole subtree), tree-depth (whole subtree for a match at level ≥ max depth − x), subtree-height (whole subtree if it is ≤ x levels deep), levels-below (x levels under each match)
filterDescendantDepth filter-descendant-depth number Experimental. The x of the depth-limited filter scopes (default 1)
shouldExpandFilterDescendants expand-filter-descendants boolean Experimental. Expand the descendants a filter scope adds (default true); off, they start collapsed
Event Twin Detail Fires when
index-progress onIndexProgress { processed, total, isComplete } The async index filled another batch, and once more with isComplete: true at the end — results are partial until then
search-status-change onSearchStatusChange { searchTerm, matchCount, isLimited, limit, isIndexing } A filter was applied or cleared (also the automatic re-filter when indexing completes); isLimited = more matched than max-search-result-count

SF04 · Filter Scope

Which descendants of a filter match stay visible. Ancestors always do. Same term + same x (filterDescendantDepth) across five filterScope values. The org chart is ragged: Sales is 6 levels deep, Marketing 5, IT / Finance / Operations 4, HR only 3. Bold = an actual match; the rest is context.

tree-depth threshold = level ≥ 4

Legend

Every mode shows the matches and all their ancestors; the mode only decides which descendants of a match are added. Levels count from the top: Acme Corp = 1, divisions = 2, … people in Sales = 6 (the tree's max depth).

filterScope Descendants added for a match What x means Good for
matches None — just the match (default). — Finding a node; the smallest result.
descendants Its whole subtree, always. — "Show me everything under Sales".
tree-depth Its whole subtree, but only if the match sits at level ≥ (tree's max depth − x); else none. Judged against the deepest branch of the whole tree. How far up from the tree's bottom level a match may sit and still expand (now: level ≥ 4). Smaller x = only matches near the bottom. Uniform-depth trees, where "near the bottom" means the same everywhere. On this ragged chart a shallow branch (HR, IT) behaves differently from Sales.
subtree-height Its whole subtree, but only if that subtree is ≤ x levels deep; else none. Judged per match, from the match down. The biggest subtree worth unfolding (0 = leaves only). Ragged trees: expand small teams, keep a whole division folded.
levels-below Exactly x levels under every match (deeper levels hidden). How many levels to show beneath each match. Previewing the next level or two, e.g. "Division" + x=1 = its teams.

shouldExpandFilterDescendants (the checkbox above) only affects the rows a mode adds: unchecked, they're in the tree but start collapsed — the cheap option on big trees. 

<web-treeview
  search-value-member="name"
  filter-scope="subtree-height"      <!-- matches | descendants | tree-depth | subtree-height | levels-below -->
  filter-descendant-depth="2"        <!-- x -->
  expand-filter-descendants="false"  <!-- added subtrees start collapsed -->
></web-treeview>

SF05 · Scroll control (beforeScrollCallback)

The tree scrolls a node into view on its own in three places: a keyboard move (source: 'keyboard' — nearest, always instant), scrollToPath ('scroll-to-path' — center, the --wtv-scroll-behavior token, and it first scrolls the page to the tree when the tree is off-screen) and the reveal after a paste into a node ('paste'). Each scroll moves only the tree's scroll container, never the page; a tree without one scrolls the page with the same alignment. beforeScrollCallback runs first: return false to skip the scroll, or options to replace the defaults. Type to jump with scrollToPath, or click a node and use the arrow keys / PageDown / End. Scroll the page so the tree is out of sight, then search with “Reveal the tree” on and off.

ctx fieldTypeDescription
node / pathLTreeNode / stringThe node being revealed
source'keyboard' | 'scroll-to-path' | 'paste'What made the tree scroll

options{ block, inline, behavior, shouldRevealContainer }What the tree is about to use; return a partial to replace it

beforeScrollCallback ctx:

tree.beforeScrollCallback = ({ source, path, container, options }) => {
  if (source === 'keyboard' && cancelKeyboard) return false;    // skip it
  if (source === 'scroll-to-path') return { block: 'start' };    // replace a default
  // nothing → the defaults in `options`
};

// scrollToPath brings an off-screen tree into view first — opt out per call:
tree.scrollToPath('27.5', { shouldRevealContainer: false });
